# `src/server`: data, identity, and the server entry points

The app's server side, in two halves. **The BFF**: server actions, read models, the on-demand read routes,
autosave, import, the request context and the sign-in stand-in. It reaches its backend only through the service
interfaces in [services/](services/README.md) (`services()`), with the request context from
[context/request.ts](context/request.ts); it holds no data, reads no clock and decides nothing: it parses, words and
lays out.

**The backend** is today the local implementation behind those interfaces ([services/local/](services/local/)) with
the Drizzle schema and client ([db/](db/)), the demo seed and the reset: the code the Java API replaces. Business
rules live in neither: they live in `src/domain`, which both call and which may not import this layer. Client
components call the server actions and import one pure module, [starters/catalog.ts](starters/catalog.ts). Outside
this layer, only [scripts/db-migrate.ts](../../scripts/db-migrate.ts) and route tests import the database client.

## How to read a file here

A file's header comment is its contract: what it holds, what it leaves to others, and, in a service file, the order
its steps run in. A `/** */` comment documents an export. A `//` comment records a decision at the line it applies to.
[services/local/command.ts](services/local/command.ts) shows all three: its header lists the steps of every command
in order, `CommandSteps` documents each step, and the comment inside `runCommand` says why a returned refusal rolls
back too.

## Rules

Lint-enforced by [eslint.config.mjs](../../eslint.config.mjs) for every file under `src/server`:

- No `@/editor` import: there is no barrel. Import the server-safe modules `@/editor/schema` (`baseExtensions`, `BaseExtensionOptions`, `ensureBlockIds`), `@/editor/model/*`, and `@/editor/paste/*`, and only those the editor README's Public API lists (lint enforces it).
- No `@/components` import: server code never loads the React UI. A type or constant a screen and the server share goes in `src/domain` (`SubmitSummary`, the `ucomp_created` cookie); a pure helper goes in `@/editor/model/*` (`listSets`).
- No simulator data: `@/server/db/schema/sim`, `**/schema/sim`, and `@/simulator/*` are banned. `seed/**` and `reset.ts` are exempt because they write the simulator's tables.
- `"use server"` appears only in [actions/](actions/), as a file's first line or inside a function: everywhere else in `src` (the simulator's own `src/simulator/actions.ts` aside) it is a lint error. The directive makes every export a public POST endpoint that takes any input, so server actions are for mutations only, and each parses its input with zod.
- Rules on other layers that protect this one: `src/domain` may not import `@/server/*`, and `src/simulator` may import only `@/server/db/schema/sim` from it.
- The backend seam's rules ([services/README.md](services/README.md#the-rules)): only the local implementation, `db/` and the seed talk to the database, and only `services/index.ts`, `/api/v1`, the seed, the reset and tests import an implementation; only the backend reads the clock; only the domain and the implementations decide with `can()`; and only the backend, the fake, the contract suite and tests import the reset, the seed or the test support.

Convention only (no lint rule):

- Every module that imports the `db` client, the clock, or `next/headers` is marked: `import "server-only"`, or `"use server"` in action files. Pure helpers and modules that take the database as an argument ([ids.ts](ids.ts), `seed/`, most of `import/`, [drafts/parse-patch.ts](drafts/parse-patch.ts), the web and email channels) aren't.
- [services/local/clock.ts](services/local/clock.ts) is the only reader of the current time, and the backend's clock: the BFF reads none (lint). A command reads it once, before its transaction (`runCommand`), and passes it down as `at` or `now`; a read that decides by time answers it as `asOf`. Domain functions take it as an argument.
- The local implementation loads facts, asks `src/domain` what may happen, and writes the answer. A new rule goes in `src/domain`.
- Inside `inTransaction`, read and write through `tx`. Writes take turns on one process-wide lock that a transaction holds until it ends, so a write through `db` inside one waits for that same transaction to end. It stalls for the 5 s turn wait and fails as `SQLITE_BUSY`.
- A `"use server"` file may export only async functions (type exports are erased, so they're fine). That is why an action file's own helpers are private, and why the helpers every action shares live in [actions/kit.ts](actions/kit.ts), which isn't `"use server"`.

The functions in [queries/](queries/) that pages and routes call. Each reads the request context, asks a service for
facts, and words and lays them out.

## Anatomy of a mutation

Every action runs on the server action kit, `serverAction` in [actions/kit.ts](actions/kit.ts): the action
declares its steps, and the kit runs them in one order. The kit is a plain `server-only` module, not `"use server"`,
so its helpers are shared instead of copied into each action file. Every action declares `call`; the backend
does the rest. `setSunset` in [actions/review.ts](actions/review.ts):

```ts
"use server";
export async function setSunset(input: {
  templateId: string;
  versionNumber: number;
  sunsetAt: string;
}): Promise<ActionResult> {
  return serverAction(input, {
    // 1. the request context
    input: SunsetInput, // 2. parse (zod)
    call: (ctx, { templateId, versionNumber, sunsetAt }) =>
      // 3. the service decides and writes
      services().review.setSunset(ctx, {
        templateId,
        versionNumber,
        sunsetDay: sunsetAt,
      }),
    after: ({ changed }) => {
      // 4. revalidatePath(…) + refresh()
      if (changed) refreshAfter();
    },
  }).then(withoutChanged);
}
```

and behind it, the local implementation's command in [services/local/review.ts](services/local/review.ts), on the
command kit (`runCommand` in [services/local/command.ts](services/local/command.ts)):

```ts
setSunset: (ctx, input) =>
  runCommand(deps, ctx, input, {
    authorize: async ({ ctx, input }) => {
      const found = await findVersion(input.templateId, input.versionNumber); //    read only to learn the team
      check(ctx.viewer, "version.setSunset", { teamId: found?.teamId ?? null }); // a. permission
      if (!found) refuse(REQUEST_REFUSALS.versionGone);
      if (!isCalendarDay(input.sunsetDay)) refuse(REQUEST_REFUSALS.invalidDate);
      return found;
    },
    transaction: async (tx, { ctx, input, found, now }) => {            // b. the clock once, then one transaction
      const version = await loadVersion(tx, found, input.versionNumber); //    re-read inside it
      const zone = await readBusinessZone(tx);                          //    and the settings it needs
      if (sunsetUnchanged(version, input.sunsetDay, zone, now)) return { ok: true, changed: false }; // a double click
      const outcome = setSunsetTransition({ version, sunsetDay: input.sunsetDay, zone, now, … }); // c. the domain decides
      if (!outcome.ok) refuse(outcome);
      await updateVersion(tx, version, outcome.changes, now, deps.hooks); // d. compare-and-set
      await writeEffects(tx, outcome.effects, effectContext(ctx.viewer, found, version.id, now)); // e. effects
      return { ok: true, changed: true };
    },
  }),
```

1. The request context ([context/request.ts](context/request.ts)): the viewer (`getViewer()`, [viewer.ts](viewer.ts)), or none when nobody is signed in, which the kit answers with `signed_out` before anything else. It carries no time: the backend reads its own clock.
2. The input is parsed with zod. Input that doesn't parse is refused with `REQUEST_REFUSALS.invalidInput()` ("Check the form and try again."), or with the action's own refusal (`invalid`): access actions give the parser's first problem, `markNotificationRead` answers `notification_gone`.
3. `call` asks the service with the context and the input, and its answer is the action's: `{ ok: true, … }` or `{ ok: false, code, reason }`. The action decides nothing ([decision 0070](../../docs/decisions/0070-rules-and-permission-checks-sit-behind-the-service-interfaces.md)). Behind it, in the local implementation:
   - a. `authorize` reads the record outside the transaction, only to learn its team and people, then checks: `check(viewer, action, resource)` asks `can()` from `@/domain/permissions`, and `permit(result)` takes a domain rule's answer (`canComment`, `canActOnThread`). An unknown id gives `teamId: null`, so a missing record and a forbidden one fail the same way. Then it refuses what the request can't be: the record is gone, a note is too long, a date isn't one. It returns what the transaction needs (`found`).
   - b. `transaction` runs inside `inTransaction(db, …)`, once: a write that can't get the database within the client's wait fails as `SQLITE_BUSY`, a bug like any other ([Database](#database)).
   - c. A transition from `@/domain/lifecycle/*` returns `{ ok: true, changes, effects }` or `{ ok: false, code, reason }`. The command writes `changes`; it doesn't decide.
   - d. `updateVersion` ([services/local/version-rows.ts](services/local/version-rows.ts)) updates only while `state`, `rev`, and `currentStage` still match, and bumps `rev`. A miss is refused `version_changed` (someone else changed the version between the read and the write), so nothing is written over; approve steps the Active version down with a compare-and-set of its own.
   - e. `writeEffects(tx, effects, ctx)` ([services/local/effects.ts](services/local/effects.ts)) writes audit rows, notifications (to a user or a team role, never to the actor; each stores its kind, its facts and its link placed by team id, never a sentence or a URL, decision 0055), and consumer notices (consumers with a non-preview render of the template from 90 days before `ctx.at` on), all in the same transaction. `ctx.at` is when it happened and dates the audit rows; `ctx.writtenAt`, which only the sunset sweep sets, dates the notifications and notices when it's later.
4. `after` runs only once the service answered `ok`: `revalidatePath()` for the other routes that show the change, then `refresh()` to re-render the page the person is on, and `redirect()` last (`startDraft`, `createTemplate`). Next's redirect passes through the kit untouched. Route handlers can't call `refresh()`; they use `revalidatePath()` (`src/app/api/imports/route.ts`).

**Refusals.** `refuse(refusal)` anywhere in `authorize` or the transaction throws a `RefusalError` ([services/refuse.ts](services/refuse.ts)), which rolls the transaction back and becomes `{ ok: false, code, reason }`; a transaction that returns a refusal is rolled back the same way. Anything else thrown is a bug and propagates. Every refusal is an entry from a domain table ([domain/refusals.ts](../domain/refusals.ts)); what the command checks before the rule runs (input, a record that's gone, a compare-and-set that missed) comes from `REQUEST_REFUSALS`.

**Compare-and-set.** SQLite serializes writes, so here only a test reaches a missed compare-and-set, through `TestHooks.beforeCompareAndSet`; the Java API reaches it when two people act at once. The `rev` bump also makes an autosave still in flight fail rather than land on a frozen version. When the person acts on content they were shown, the client sends the `rev` it was shown with: `submitVersion` takes the submit summary's `rev`, and `submit` refuses with `REFUSALS.summaryStale` (code `summary_stale`) when the draft changed after the summary was read.

The result type is `ActionResult<T>` from `@/domain/review-types` (`({ ok: true } & T) | Refused`, where `Refused` is `{ ok: false; code; reason }`), re-exported by `@/domain/access-types`. The browser runs actions with `useActionRun` (`src/components/primitives/use-action-run.ts`).

Variations today:

- The access and platform commands ([services/local/access.ts](services/local/access.ts), [services/local/platform.ts](services/local/platform.ts)) write through `applyMembershipChange` and `writeAccessEffects`; `saveApprovalChain` also calls `writeEffects` with a notification it builds itself. A setting saved as it already is answers `changed: false`, and its action refreshes nothing.
- An access command refuses a request, membership or review that's gone with its own sentence before the permission check, since a colleague acting first deletes it, and checks the last Team Admin again once its change is written (`lastAdminRefusal`).
- Locally, an access command that reads its clock runs the scheduled jobs first, each in its own transaction, so a refusal doesn't roll a sweep back (the lazy trigger; [Clock, viewer, and the access sweep](#clock-viewer-and-the-access-sweep)).
- `startDraft` and `createTemplate` answer a refusal (a newer version in review, a viewer who can't edit or create) and redirect on success. `createTemplate` takes the kind the author chose (`family`, Document or Alert) with a starter of that kind.
- `createTemplate` resolves the URL's team slug to its id (`identity.space`), asks the backend which content type the kind is made on (`templates.newTemplateType`, whose `asOf` dates the starter's sample values: the BFF reads no clock), builds the starter, fits it to that content type, prepares its documents, and hands the draft to `templates.create`, which draws the template id and stores it. Import always makes a document and does the same with the file's conversion (`templates.createImported`).
- [actions/demo.ts](actions/demo.ts) and [actions/persona.ts](actions/persona.ts) are demo tools behind `services().demo`: no permission to check, and the demo flag checked before the kit runs, so with it off they answer `demo_mode_off` before reading their input. Input they can't use is answered with `invalid_input`.

## Anatomy of a read

Pages and components never run SQL. A page renders an async server component inside `<Stream>` (`src/components/primitives/stream.tsx`, a `Suspense` boundary). That component, in `src/components` or in the page file itself, awaits `params` and calls a read model. For example, `src/app/(product)/[team]/templates/[templateId]/versions/page.tsx` renders `src/components/versions/versions-content.tsx`, which calls `getVersions()` from [queries/versions.ts](queries/versions.ts).

`getVersions` is the shape every read model takes: it reads the request context (`requireRequestContext()`), asks the service for the facts and the decisions (`services().versions.history`), and words and lays them out (labels, contract lines, people, one entry per number); it decides nothing. The service answers the instant it decided at (`asOf`), and the read model hands it to the screen (`now`), so the screen counts its dates from the backend's clock, never its own. The wording and the layout are one pure function (`versionsData(history)`), tested on facts.

A read model:

- is usually wrapped in React `cache()`, so calls within one request share a result. Nothing in `src` uses `"use cache"`; every read happens at request time.
- checks access first, and shows the Not found page for what the viewer may not read, the same as for what doesn't exist ([decision 0052](../../docs/decisions/0052-a-page-you-may-not-read-is-not-found.md)). Under Cache Components the page streams, so that response is HTTP 200 with `noindex`, not a 404; only the `/api/*` route handlers send real statuses.
- gates the space and the template the way `getVersions` does. `requireSpace(slug)` is Not found for an unknown team and for a team the viewer can't see. The service answers 404 for a template the viewer may not see, and the read model calls `notFound()` for that and for a template on another team than the URL's space (compared by team id). The review screen hands the space to `review.screen`, which decides which round the URL opens (`roundToOpen`).
- turns a permission refusal into `notFound()` when the read needs a permission: the settings sections ([queries/access.ts](queries/access.ts), [queries/platform.ts](queries/platform.ts)) and the Audit page ([queries/audit.ts](queries/audit.ts)) ask the service, which decides and refuses it (403 `generic`, or 404 for a team that isn't there). They read the request context, which reads cookies, so the caller must sit inside Suspense. Nobody signed in goes to sign in (`signInRequired()`), not to Not found.
- takes the time from the service's answer (`asOf`); it reads no clock.
- returns a plain, serializable type declared beside the query (`VersionsData` in [queries/versions.ts](queries/versions.ts), `ReviewScreenData` in [queries/review-models.ts](queries/review-models.ts), `ThreadView` in [queries/threads.ts](queries/threads.ts)); the settings and audit models (`MembersSection`, `AuditPageData`, …) are in [queries/access-models.ts](queries/access-models.ts). A component imports the type with `import type` from the query's module. A type a domain rule takes or returns stays in `src/domain`.
- sends dates as ISO strings (`iso()`, `isoOrUndefined()`), days as `YYYY-MM-DD` (`utcDay()` from `@/domain/dates`), and people as `Person` (the read's `people`, looked up with `personOf()` from [src/domain/people.ts](../domain/people.ts)).
- carries permissions decided: `can: { <action>: PermissionResult }`, so a client component can disable a control and show the reason without calling `can()`, and tell one refusal from another by its `code`. See `versionActions()` in [domain/lifecycle/version-actions.ts](../domain/lifecycle/version-actions.ts), which the service decides with.
- carries, for the settings sections, what each action does (`consequences: { <action>: string }`), worded from the service's facts with the domain's wording functions and the read's `asOf`, so a screen never words a rule or works out a deadline. `getMembersSection()` in [queries/access.ts](queries/access.ts) words `AccessService.members`' facts (`membersSection(facts, viewerId)` is the pure part).

Every read model answers ISO strings and decided `can` results. The Library's, `getLibrary` ([queries/library.ts](queries/library.ts)), words its rows' ages (`lastEdited`) from the facts' `asOf` and carries the decided `canCreate`.

Reads a screen makes on demand, when a dialog or a menu opens, are GET route handlers under `src/app/api/templates/[templateId]/`, never server actions: an action is a public POST endpoint that runs one at a time with the page's mutations, so a read would hold up Edit or Submit (or wait behind them).

A route reads the request context (`requestContextOrRefusal()`, 401 without a viewer) and hands the raw request values to the service's read, which parses them, checks the permission, writes nothing, and answers a `ReadResult` ([api/reads.ts](api/reads.ts)): the data, or a refusal with its code, its sentence and a status (400 unparsable, 401 signed out, 403 may see but not do this, 404 no such template or version or not the viewer's to see, 409 not in a state to read). `readResponse()` sends the answer as the `ActionResult` the client reads, uncached. The five:

| Route (`/api/templates/[templateId]/…`) | Read                                                                                                                         | For                                                                                                                                              |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `compare?from=&to=`                     | `services().versions.compare` ([queries/compare.ts](queries/compare.ts) names its answer `ComparePair`)                      | The Compare dialog, per pair of versions: the template's family, and each version's name, body, channel fields and SMS footer (`template.view`). |
| `base-version?draft=`                   | `services().versions.baseVersion` ([queries/base-version.ts](queries/base-version.ts) names its answer `BaseVersionContent`) | "Revert to v3" (`draft.edit`).                                                                                                                   |
| `submit-summary`                        | `getSubmitSummary` ([queries/submit-summary.ts](queries/submit-summary.ts))                                                  | The submit dialog, and its Refresh summary (`version.submit`): `services().review.submitSummary`'s facts, laid out by `submitSummaryOf`.         |
| `copilot-prompt`                        | `getCopilotPrompt` ([queries/copilot.ts](queries/copilot.ts))                                                                | The Copilot prompt dialog (`draft.edit`).                                                                                                        |
| `integration`                           | `loadIntegrationPanel` ([queries/integration.ts](queries/integration.ts))                                                    | The SHARE panel, prefetched on hover or focus of the ring (`integration.view`).                                                                  |

The ⌘K palette's search is the same kind of read: `GET /api/palette/[space]?q=&template=` calls `searchPalette` ([queries/palette.ts](queries/palette.ts)), which parses the values (a `q` longer than `PALETTE_QUERY_MAX` is a 400), resolves the space's slug to its team with `identity.space` (404 for a space the viewer can't see), and asks `templates.palette` for what was typed. The palette asks it when it opens and as the viewer types; no page carries templates ([decision 0024](../../docs/decisions/0024-the-palette-searches-on-the-server.md)).

The backend lists the space's templates ranked by `paletteTemplates` in [src/domain/palette.ts](../domain/palette.ts) and decided by `paletteSearch` in [src/domain/palette-search.ts](../domain/palette-search.ts): rank, then name, then id by code point. At rest it answers Recent (newest first, the later write first among rows at one instant) and a first page; while searching, the best matches. It also answers `can.create` and whether the template being viewed is the viewer's to see.

The consumer API's reads in [services/local/consumer-api.ts](services/local/consumer-api.ts) have no viewer: `requireConsumer()` checks the `X-Consumer-Id` header. `/api/v1` is the backend's own API (the Java API serves it to consumers directly after the port, [decision 0057](../../docs/decisions/0057-consumers-authenticate-with-client-credentials.md)), so its reads sit in the local implementation beside the services and keep their own tests; its route handlers import them there, and `withDemoDate` (the demo clock in the response's `Date` header) with them.

## Database

- **Schema**: [db/schema/ucomp.ts](db/schema/ucomp.ts) holds the app's tables. JSON columns are typed with domain types, and timestamps are `timestamp_ms` integers read as `Date`. [db/schema/sim.ts](db/schema/sim.ts) holds the simulator's `sim_*` tables.
- **Channel fields**: a version's short fields of its own per channel (Email's subject and preheader; Push's title, subtitle and body; SMS's message) live in one JSON column, `versions.channel_fields`, keyed by channel and then by field key, `{ "email": { "subject": <doc>, "preheader": <doc> } }`, a field with no value left out. The registry in `src/domain/channel-fields.ts` declares them, and nothing here names a field. The workspace and a draft patch hold them flat, one key per field id (`"email.subject"`).
- **Names**: a template has no name column; each version has its own (`versions.name`), copied into a new draft, renamed only in the draft (autosave) and frozen at submit ([decision 0016](../../docs/decisions/0016-the-name-is-versioned.md)). Which one a reader takes:
  - customer output, the name of the version it renders or returns: the render's title, the JSON Schema title, a notice's `templateName` (the notice's own version, in `writeEffects`). Where `/api/v1` speaks of the template (search, detail `name`, the integration panel), the Active version's; with none Active, detail takes the version that still renders (`contractBaseline`), then the newest released.
  - a CMS screen about one version, that version's (the round's: each round is its own row): the review screen, the review queue, notifications, and an audit event about a version (in the page and the CSV export). A rename shows against what customers get today: `contractBaseline` (the submit summary's `baseline`, and the review screen's `liveName` through `renameBaseline`, which shows a round sent back before its number went live against what it was drafted from).
  - every other CMS screen, the open draft's name, otherwise the newest version's, and the template id when there's no version: `latestVersion` in [src/domain/rounds.ts](../domain/rounds.ts) over a version list, or `currentName()` ([services/local/template-name.ts](services/local/template-name.ts)) as a SQL column.
- **Client**: [db/client.ts](db/client.ts) exports `db` (Drizzle over libSQL, ucomp schema only), `libsql`, `Db`, and `DATABASE_URL`. The default is `file:./data/ucomp.db`. A remote libSQL database (Turso) isn't a supported deployment: the client's write lock and the code's read-check-write rules assume one local file and one process, and the Java API replaces this layer. e2e sets `DATABASE_URL` to its own file, and `UPLOADS_DIR` (below) beside it. The simulator opens the same file through its own client, `src/simulator/db.ts`.
- **Migrations**: [db/migrations/](db/migrations/) holds the SQL files and `meta/` snapshots, generated from both schema files ([drizzle.config.ts](../../drizzle.config.ts)). To add one: edit the schema, run `npm run db:generate`, read the SQL, then apply it with `npm run db:migrate` or `npm run db:reset`. `db:migrate` runs [scripts/db-migrate.ts](../../scripts/db-migrate.ts) with `--conditions=react-server` so `server-only` loads. Nothing migrates at app start. Tests migrate their temp databases from the same folder. If seeded rows need a new column, update `seed/`.

SQLite and libSQL specifics:

- Drizzle's `db.transaction` opens libSQL's default write transaction, `BEGIN IMMEDIATE`, so reads inside it see the `rev` the update will check.
- `createAppClient()` in [src/lib/serialized-writes.ts](../lib/serialized-writes.ts) makes every write in the process take turns on one lock, shared with the simulator's client. Plain reads don't wait. A write waits up to `WRITE_TURN_WAIT_MS` for its turn, then fails as `SQLITE_BUSY`. The client's busy `timeout` (`BUSY_TIMEOUT_MS`) covers locks held by other processes, such as the e2e helpers. That file's header explains why an in-process busy collision must never happen.
- Every URL gets the client, a remote one too, because invariants such as the notice counter and last-admin hold only while writes take turns. A remote libSQL database isn't a supported deployment (the Java API replaces this layer).
- That client is the only place a write waits, and nothing retries a write that failed: a server action, an autosave or a sweep stuck behind a long write fails rather than spin. Don't add a busy retry above the client; each attempt would wait again.
- Another process holding the file's lock is the worse case: libSQL's busy wait blocks the Node event loop for up to `BUSY_TIMEOUT_MS` per statement, so the server answers nothing (reads included) and the queued writes fail one after another until the lock clears. Run `npm run db:reset` or an e2e helper beside a live server only knowing that.
- `inTransaction(db, run)` ([services/local/transaction.ts](services/local/transaction.ts)) runs one write transaction, once. Use it for every write transaction. The second of two writes reads after the first commits, so its compare-and-set sees the first one's change.
- Partial unique indexes on `versions` (`versions_one_draft`, `versions_one_active`) enforce one open draft and one Active version per template. `startDraft` relies on this when two people press Edit at once.
- A version number has a row per round (`versions.round`, set at submit with the number; [domain/rounds.ts](../domain/rounds.ts)). `versions_template_number_round` makes (template, number, round) unique, and the partial index `versions_one_released` allows one released row (Active, Superseded or Revoked) per (template, number). NULLs stay distinct, so drafts, which have neither, pass both. Migration `0008_review_rounds.sql` set every existing submitted row to round 1 and renumbered nothing.
- `consumer_notices.seq` numbers the outbox in commit order, and the notices API pages on it. `writeEffects` takes the next numbers with `takeNoticeSeqs(tx, count)` inside its transaction, which holds the write lock until it commits, so a notice that becomes visible later always has a higher `seq`. `created_at` can't do this: the command read the clock before its transaction, so two commands can commit in the other order.
- The last number taken lives in `settings.consumer_notice_seq` and only goes up, so deleting the newest notices (as e2e cleanup does) never hands their numbers out again. A unique index refuses a repeated number. Every insert into `consumer_notices` must take its `seq` this way; the seed numbers its notices 1…n by time and stores n.
- A demo reset starts the numbers again. The notice cursor carries `settings.seeded_at` as its epoch (`noticeEpoch` in [services/local/consumer-api.ts](services/local/consumer-api.ts)), so a cursor from before a reset is refused rather than read against the new numbers.

**Seed and reset.** `seedDatabase(db, { base })` ([seed/index.ts](seed/index.ts)) builds every row in memory ([seed/context.ts](seed/context.ts)), deterministically (named `mulberry32` sequences, `seededId()`), with timestamps relative to `base`. It inserts in foreign-key order and returns template ids by seed key, which tests use. Every send-back is seeded as `requestChanges` writes it, with a whole-version thread holding the reason that the next round's submit resolves; the build refuses one without it.

A template and each of its versions carry their ids as literals in the spec, because e2e specs, golden files and screenshots name them ([decision 0069](../../docs/decisions/0069-seed-ids-are-literal-and-the-seed-exports-a-fixture.md)). Every other row draws its id from a sequence named for its template, team or module (`ctx.id(scope, prefix)`), so adding a row moves only the later ids of its own kind in its own scope ([seed/README.md](seed/README.md#ids)).

`resetDemo()` ([reset.ts](reset.ts)) drops every table, re-runs the migrations, seeds from the current time, zeroes the clock offset, and empties the uploads folder (`defaultUploadsRoot()`: `UPLOADS_DIR`, else `./data/uploads`). It refuses, before it touches anything, a database whose `DATABASE_URL` isn't a local `file:` URL (`reset_needs_local_file`, `DEMO_REFUSALS` in [src/domain/demo.ts](../domain/demo.ts)), whatever the demo flag says. `npm run db:reset` and `resetDemoAction` call it.

A fresh clone needs `npm run db:reset` before any page can load a viewer. `npm run seed:export` writes the same rows as a JSON fixture with times relative to the reset, for the Java side ([seed/README.md](seed/README.md#the-fixture)).

The platform ([seed/platform.ts](seed/platform.ts)) has two content types, each with a one-stage chain: Disclosure (documents: PDF, Web and Email, three required sections) and Alert (messages: Push and SMS, no sections, the SMS footer "Coral: Reply STOP to opt out, HELP for help." and a 3-part budget). Every seeded team has an app name and a fictional short code its messages come from, so no preview shows the fallback: Coral Offers sends as "Coral" from 26725, Deposits as "Deposits Online" from 33767, and Card Statements as "Card Center" from 22737 ([seed/teams.ts](seed/teams.ts)).

The submit command reads the content type's footer and budget with `loadMessageRules` ([services/local/chain.ts](services/local/chain.ts)) and freezes the footer into the version (`versions.sms_footer`): render, the review screen, Compare and Coral print a submitted version's own footer, and only a draft takes the content type's as it stands (`smsFooterOf`). The template's family comes from its content type too (`loadFamily`, `contentTypeFamily`), never a version's channels.

The workspace's and the review screen's read models carry the message rules and the team's senders (`messageRules`, `senders`) for the message composer and the phone preview, which render in the browser ([decision 0036](../../docs/decisions/0036-message-previews-resolve-in-the-browser.md)). The workspace's also says which family the template is (`family`), which picks the editor or the composer.

The templates are declared in [seed/templates/](seed/templates/), one `SeedTemplate` each, and `buildTemplate` ([build.ts](seed/templates/build.ts)) derives every row from it: the template, its versions, approvals, comment threads, audit events and consumer notices ([seed/README.md](seed/README.md) walks through it). A template names its content type (`contentType`, Disclosure unless it says Alert), and [checks.ts](seed/templates/checks.ts) refuses a version that breaks the type's rules: its required sections in order, and only channels the type allows.

Coral Offers has disclosures ([coral.ts](seed/templates/coral.ts)), one in each lifecycle state, and alerts ([coral-alerts.ts](seed/templates/coral-alerts.ts)): Payment Due Reminder (v1 Active, rendered by Coral as push and SMS every day), Card Used Abroad (v1 waiting for an approver) and Rate Change Heads-up (a draft that pairs with the Rate Change Notice letter). An alert's body is one empty paragraph; its push and SMS are channel fields, and every seeded alert passes submit's message rules (`seed.test.ts`). Deposits and Card Statements ([deposits.ts](seed/templates/deposits.ts), [card-statements.ts](seed/templates/card-statements.ts)) have disclosures.

[seed/history.ts](seed/history.ts) writes months of renders (daily streams, previews, a few failures and the latest renders), and [seed/activity.ts](seed/activity.ts) the notifications, access requests and recertification.

**The `sim` schema** belongs to the simulator ("Coral — simulated"). In this layer only `seed/**` and `reset.ts` may import it (lint). `src/simulator/**` and `src/app/(simulator)/**` may import it and nothing else from `@/server`.

## Clock, viewer, and the access sweep

- **Clock** ([services/local/clock.ts](services/local/clock.ts)): `now()` is the real time plus `settings.clock_offset_days` days. It awaits `connection()` first, which marks the caller as request-time under Cache Components. libSQL resolves in microtasks, so without it a prerender could capture the build's `Date.now()`. `advanceClock(days)` moves the offset. It is the local implementation's clock (`localServices`), and only the backend reads it; the demo pill's readout asks the demo service for it (`demo.clockReadout`), and [queries/clock.ts](queries/clock.ts) words it.
- **Business time zone** ([services/local/business-zone.ts](services/local/business-zone.ts)): `settings.business_zone`, the zone a sunset date ends at 00:00 in (decision 0017). No row, or a zone off `BUSINESS_ZONES`, reads as `America/New_York`. Commands read it inside their transaction (`readBusinessZone(tx)`), and reads with `db`. `platform.setBusinessZone` ([services/local/platform.ts](services/local/platform.ts)) changes it; it moves no sunset already set.
- The reads hand the BFF a sunset's day (`sunsetDay`, YYYY-MM-DD), whether it has passed (`sunsetPassed`, the domain's test on `now()`; the status badge words it "Sunset passed"), and the picker's `SunsetCalendar`, never a zone or a clock to compute with.
- **Request context** ([context/request.ts](context/request.ts)): the viewer, read once per request (React `cache`), with a correlation id and a credential slot an HTTP backend will fill. It fails closed: no viewer, no context; a page then goes to `signInRequired()` ([context/sign-in.ts](context/sign-in.ts), today the static `/sign-in` page, Better Auth's sign-in later). Every page, action and route reads the viewer through it, and no clock.
- **Viewer** ([viewer.ts](viewer.ts)): there is no login. `getViewer()` (React `cache`) reads the `ucomp_persona` cookie and asks the identity service whom it names (`services().identity.viewer`), a `Viewer` (`@/domain/types`) with memberships and roles; each membership names its team by id and by slug, which are never the same (decision 0053). A missing cookie or an unknown user is nobody (signed out), unless the demo tools are on (`DEMO_MODE`), where it falls back to `DEFAULT_PERSONA`, `"maya"` (handoff review S2).
- **Personas**: `getPersonaSummaries()` in [queries/personas.ts](queries/personas.ts) words the switchable personas the demo service lists (`demo.personas`). The persona switch reads no viewer itself: the demo service answers where the new persona lands (`demo.switchPersona`), so the request context stays `getViewer()`'s only reader.
- **Spaces** ([queries/spaces.ts](queries/spaces.ts)): the URL names a team by its slug; `requireSpace(slug)` resolves it, once per render, to the team's id with what the viewer may do there (`services().identity.space`), and `getShell()` lays out every space the viewer may switch to (`identity.shell`). Everything below them (permission checks, queries, services) takes the team's id; a link takes the slug.
- **The scheduled jobs** ([services/local/sweeps.ts](services/local/sweeps.ts)): `runScheduledJobs(at)` runs the access sweep, then the sunset sweep, each at the instant it is given and in its own transaction. After the port they are the Java API's scheduled jobs; the contract suite runs them through `runScheduledJobs` on both implementations ([services/contract/sweeps.ts](services/contract/sweeps.ts)).
- Here they run from the demo service when the clock moves (at the clock it moved to), on a persona switch (before stamping `last_active_at`), and, the local implementation's lazy trigger, when an access command reads its clock once its permission check has passed ([services/local/access.ts](services/local/access.ts)). They don't run on a timer or on page reads.
- **Access sweep**: `runAccessSweep(at)` applies every access deadline `at` has crossed (recertification lapses, the 90-day inactivity flag, the 120-day suspension), backdated, in one transaction. It checks outside a transaction first, so a sweep with nothing to do takes no write lock, and running it twice changes nothing.
- **Sunset sweep**: `runSunsetSweep(at)` writes a `version.sunset_passed` audit row and a `sunset_passed` consumer notice, through `writeEffects` with a null actor, for each sunset `at` has passed that nothing records yet. `sweepSunsets` in `@/domain/lifecycle` decides; `recordedSunsets` is the one read of the audit log behind "nothing records" (the `versions.sunset_recorded_at` column after the port, decision 0066).
- Each sunset row is dated at its sunset and names the day in the business time zone. The notice carries the same instant, day and zone and the template's Active version, goes to the consumers that rendered the template from 90 days before the sunset on, takes the next `seq`, and is created when the sweep runs (`writtenAt`), so it can arrive after the sunset.
- Like the access sweep, it checks outside a transaction first, writes in one transaction, and changes nothing the second time. It only records: whether a version renders is `sunsetPassed` at render time. The scheduled trigger comes with real sign-in ([handoff review S4](../../docs/handoff-review.md#s4--high-access-deadlines-only-take-effect-when-a-demo-trigger-runs-the-sweep), [decision 0026](../../docs/decisions/0026-a-passed-sunset-is-recorded-by-a-sweep.md), [decision 0032](../../docs/decisions/0032-consumers-are-told-when-a-sunset-passes.md)).

## Render, import, autosave, and route helpers

### Render

- **The rules** are in [docs/render-spec.md](../../docs/render-spec.md), and the product rule behind them is that every channel prints exactly what the author typed and saw: no rounding, dropping, renumbering, or rewording.
- **The pipeline** is the local implementation's ([services/local/render/render-template.ts](services/local/render/render-template.ts)): `renderTemplate(input)` runs `runRender(db, input, at)` with the app database and the demo clock, and its header lists every stage and the error it returns. Stages 1–5 (template, version, who is asking, version rules, channel) need the database.
- **Which version a render finds**: a version is found by number as its head (`findRound`), so a consumer's number means the released row and an unreleased head answers 409. Only Stencil's preview route may name a `round`; a preview of an unreleased round its label names carries it into the PDF's footer and the filename (`UC-4F7K2Q-v3-round-2.pdf`).
- **The engine**: stages 6–9 are `runEngine(input, target, at)` in [engine.ts](render/engine.ts), which needs no database, clock, or request, so the golden files run the same code. The target is the channel and, for a push, its platform (`renderTarget` in `src/domain/render/errors.ts` refuses a push without one, a platform on another channel, and an encoding on push or SMS).
- **A document channel**: values, the document check ([schema-check.ts](render/schema-check.ts)), resolving to a `RenderDoc` (`@/domain/render`) and the channel's own fields to text (the registry in `src/domain/channel-fields.ts`, each field by its shape), and a channel adapter: [web.ts](render/channels/web.ts) (one HTML document, no scripts), [email.ts](render/channels/email.ts) (subject, preheader, inline-styled HTML, text), or [pdf.tsx](render/channels/pdf.tsx) (`@react-pdf/renderer`).
- **The document JSON Schema**: the structure the check parses against is also published as a generated JSON Schema, [docs/reference/document.schema.json](../../docs/reference/document.schema.json), made by [document-json-schema.ts](render/document-json-schema.ts) from `editorSchema()` for the Java engine to validate with ([decision 0065](../../docs/decisions/0065-documents-are-validated-against-a-generated-json-schema.md)). `npm run document-schema:update` rewrites it, and `npm test` fails when it is stale or disagrees with the check.
- **A message channel**: the body is never read. The engine checks the values and the field check, then calls [push.ts](render/channels/push.ts) or [sms.ts](render/channels/sms.ts), each a thin call into `renderMessage` (`src/domain/render/message.ts`), the function the browser preview runs too. It resolves the fields, adds the content type's SMS footer, measures the push's payload or the SMS's parts, and refuses past the limit with 422 `push_payload_too_large` or `sms_too_long`, which the route doesn't log as a failure.
- **The PDF** embeds fonts read from `node_modules` ([pdf-fonts.ts](render/channels/pdf-fonts.ts)) and refuses to render (`UnrenderableCharactersError`) when they can't draw a character, rather than substituting one. [html.ts](render/channels/html.ts) is the markup web and email share, and [look.ts](render/channels/look.ts) holds the colors all three use.
- **The render log**: [log.ts](services/local/render/log.ts) writes one `render_log` row per render that reached a known version, never the values: the channel, a push's platform (iPhone or Android, null for every other channel; [decision 0039](../../docs/decisions/0039-the-render-log-keeps-a-pushs-platform.md)), the outcome and the error code.
- **Two callers** run the pipeline. The consumer route, `src/app/api/v1/templates/[templateId]/render/route.ts`, calls `renderTemplate` with `preview: false` for a registered `X-Consumer-Id` (the simulator and outside consumers, no session): it is the backend's own API.
- Stencil's own preview, `src/app/api/templates/[templateId]/preview/route.ts`, asks `services().render.preview` ([services/local/render.ts](services/local/render.ts): `preview: true`, the request context's viewer, logged under the request's correlation id; [decision 0047](../../docs/decisions/0047-stencils-preview-is-its-own-route-and-api-v1-serves-consumers-only.md)). Nobody signed in previews nothing: the route answers 401 `signed_out` without asking the backend.
- Both routes read and answer through [api/render-http.ts](api/render-http.ts); `src/components/preview/render-preview.ts` calls the preview route.
- Everything here that differs by channel is a `switch` ending in `assertNever` (`src/domain/assert-never.ts`) or a `Record<Channel, …>`: the engine's adapter, the route's response, the file extension.

### Import

- **The route**: `POST /api/imports?team=` (`src/app/api/imports/route.ts`) calls `importPermission()` before reading the body (the team's slug resolved by `identity.space`, then `templates.createPermission`), reads it with `readBodyCapped()`, then calls `importTemplate()` ([import/create.ts](import/create.ts)).
- **The draft**: `importTemplate()` sniffs the kind from the bytes, converts, asks the backend which content type documents are made on, builds the draft, fits it and runs `prepareBody()` (a document the check refuses is refused as `import_content`, and nothing is sent). It hands the draft, the original, the report and a .docx's Compare HTML to `templates.createImported`.
- **The storage**: the backend stores the template, the draft, the upload row and the audit event in one transaction, and the files under `./data/uploads/<uploadId>/` ([services/local/uploads.ts](services/local/uploads.ts)), removing the folder if the write fails.
- **The Original tab** reads them back through `importOriginal` and `importOriginalView`, and the workspace's document carries the original (`importOriginal`); [queries/import.ts](queries/import.ts) words the view (the report's lines, the file's URL, a text file's text).
- **The converters**: mammoth and pdf.js run in a worker thread ([isolate.ts](import/isolate.ts) starts [convert-worker.mjs](import/convert-worker.mjs)) with a 256 MB heap and a 30 s timeout. A .docx's zip claims are checked before that ([zip-limits.ts](import/zip-limits.ts)). The worker's path is joined to `process.cwd()` and constructed through `Reflect.construct` so Turbopack leaves it unbundled; keep its imports to packages.

### Autosave

- **The route**: `PUT /api/drafts/[versionId]` is a route handler, not an action, because server actions run one at a time per client. It reads the request context (401 `signed_out` without one), then asks `services().drafts.saveAccess` from the version id in the path before reading the body, so someone who can't edit the draft is answered without a byte of it read: `version_gone` (404) for a version that isn't there or the viewer may not see, the permission refusal `generic` (403) for someone who sees it but may not edit. Then it reads the body with `readBodyCapped()`.
- **The patch**: [parse-patch.ts](drafts/parse-patch.ts) checks shape and size (the name trimmed, 1 to 120 characters). [prepare-patch.ts](drafts/prepare-patch.ts) runs the body through `prepareBody()` and each channel field the patch names (by id, `"email.subject"`; null clears one) through `prepareField(doc, field)` ([documents/prepare.ts](documents/prepare.ts)), looping over the registry (`src/domain/channel-fields.ts`): normalized for its shape (an SMS keeps its line breaks) and checked in its channel's words.
- A document they refuse is `invalid_input` (400), with the check's sentence. The client runs the same check before sending, so a patch it would refuse is never sent.
- **The save**: the route hands the prepared patch to `services().drafts.save` (the backend's, [services/local/drafts.ts](services/local/drafts.ts), deciding with `src/domain/lifecycle/autosave.ts`), which answers `version_gone`, `generic`, `version_not_draft` (409), `draft_changed` (409), then the channels' refusals, `no_channels` and `channel_unavailable` (400). `draft_changed` is a stale `rev`, unless this session's own last save produced the current one and the save was sent after it (a higher `seq`); it carries the current `rev`.
- **What it writes**: the save lays the channel fields over the version's stored `channel_fields` (read in the transaction, so the fields the patch doesn't name are kept), writes with a compare-and-set on `rev` and `state`, adds the saver to the version's `writers` (maker-checker), and keeps one `draft.edited` audit row per editing session.
- Whether this session wrote the current rev (a lost response) is `lastSaveOf`, the only read of those rows, which the Java API answers from the version row's session columns instead ([decision 0066](../../docs/decisions/0066-the-audit-log-is-the-record-and-render-events-roll-up.md)).
- Every refusal is `{ ok: false, code, reason }`, and [http.ts](drafts/http.ts) maps its code to a status (a body over the cap is `draft_too_large`, 413). No cache refresh follows a save. The client half is `src/components/workspace/autosave/`.

### Route helpers and body caps

- **Route helpers** ([api/http.ts](api/http.ts)): `correlationIdOf`, `baseHeaders`, `errorResponse`, and `jsonResponse`, used by the four `/api/v1` handlers (the preview route uses the first three); `withDemoDate`, which they wrap their handler in, is in [services/local/consumer-api.ts](services/local/consumer-api.ts), because the clock is the backend's. The GET handlers read headers before touching the database so Cache Components treats them as request-time; a POST handler always is. The drafts and imports routes have their own `respond()` helpers.

Body caps, all counted in bytes as the stream is read ([api/read-body.ts](api/read-body.ts)), after a declared `Content-Length` over the cap is refused unread: import allows 10 MiB plus 64 KiB of multipart slack, autosave 2,000,000 (`MAX_BODY_SIZE`), render 1,000,000 (`MAX_BODY_BYTES`). Each answers 413 past it. Server actions cap bodies at 1 MB, which is why import is a route handler.

Every entry point but `/api/v1` and the preview route refuses in one shape, `{ ok: false, code, reason }` (`ActionResult`), with a code from a table in `src/domain` and the status that suits it: every action, the on-demand read routes, the palette, autosave (`DraftSaveResponse` adds `rev?` to `draft_changed`), import (`ImportResponse`) and the audit export ([decision 0041](../../docs/decisions/0041-routes-refuse-in-the-actions-shape.md)). `/api/v1` and the preview route answer the render engine's `{ error: { code, message, details? } }`. Use the one your entry point already uses.

## Demo-only paths

These stand in for things a production deployment would have. The first three are the demo tools, and run only
when the server was started with `DEMO_MODE` set ([config.ts](config.ts); off when unset, so a deployment with no
environment has none of them; [decision 0051](../../docs/decisions/0051-the-demo-tools-run-only-in-demo-mode.md)).

- [actions/demo.ts](actions/demo.ts): `resetDemoAction` (the demo service drops and reseeds the database and empties uploads; the action sets the cookie to Maya) and `advanceClockAction` check no permission. With the flag off each answers `demo_mode_off` (`DEMO_REFUSALS` in [src/domain/demo.ts](../domain/demo.ts)) before it reads its input or touches anything; the local demo service checks the flag again, since it is its configuration too. `resetDemoAction` also passes on `resetDemo()`'s `reset_needs_local_file`.
- [actions/persona.ts](actions/persona.ts): `switchPersona` asks the demo service to sign in as any seeded persona, including the Platform Admin (`riley`) and the Auditor (`taylor`), without checking the caller, then sets the cookie. Flag off, it answers `demo_mode_off` and sets nothing.
- The Demo pill and the persona switcher. `DemoPillHole` (`src/components/demo/`), in `src/components/app-shell/app-frame.tsx` and `src/app/(simulator)/layout.tsx`, renders the pill only when the flag is on, and `TopBarHole` gives the profile menu its personas only then. Both read the flag at request time (inside a `<Stream>`, after `connection()` or the viewer), so one production build serves either way and the static shell never holds the build's value.
- Which workflows turn the demo tools on: `npm run dev` (`.env.development`), `npm run demo` (`cross-env DEMO_MODE=1 next start`), and the e2e servers (`webServer.env` in `playwright.config.ts`). A server you start by hand with `next start` needs `DEMO_MODE=1` for the pill and the switcher.
- The persona cookie still decides who acts, flag or no flag ([viewer.ts](viewer.ts)): turning the flag off removes the way to set it, not the cookie's authority, and a cookie set by hand still acts as that persona. That waits for real sign-in ([S2](../../docs/handoff-review.md#s2--high-identity-fails-open-to-the-default-persona)).
- `/api/v1`: a consumer is identified by the `X-Consumer-Id` header alone, with no credential, and the route reads no cookie. The preview route (`/api/templates/[templateId]/preview`) acts as the cookie's persona, so Maya by default.
- The clock offset applies to every time the app reads, and `withDemoDate` puts the demo time in `/api/v1` `Date` headers. The offset is only ever moved by the clock advance, so it stays 0 where the flag was never on.
- [services/local/uploads.ts](services/local/uploads.ts) keeps uploads in `./data/uploads`, standing in for blob storage. `defaultUploadsRoot()` is the one place that path is decided: it reads `UPLOADS_DIR` (relative to the project root) and falls back to `./data/uploads`. Reset and the local implementation both call it (`localServices({ uploadsRoot })` points a test at a folder of its own).

## Testing

Tests sit beside the code as `*.test.ts`. Run them with `npx vitest run src/server`; they never touch `data/ucomp.db`. The environment is `node`; the web and email channel tests opt into happy-dom with a `// @vitest-environment happy-dom` comment. [vitest.config.mts](../../vitest.config.mts) aliases `server-only` to `scripts/empty.ts`, so tests import server modules directly.

Tests run in a random order: [vitest.config.mts](../../vitest.config.mts) shuffles the tests inside each file, and a failing run prints its seed and the command that replays it (`npx vitest run --sequence.seed=<seed>`). A test that needs another to run first fails at once, and so does one run alone with `-t`.

**Three kinds of server test** ([decision 0068](../../docs/decisions/0068-the-bff-is-tested-against-a-fake-and-one-contract-suite.md)), as the code moves behind the service interfaces ([services/README.md](services/README.md)):

- **The BFF, without a database.** An action or a route that calls `services()` is tested against the in-memory fake: mock `@/server/services` and `@/server/context/request` with `@/server/services/fake/testing`, call `fakeBackendPerTest({ base })`, and act as a persona with `backend.as(userId)` ([actions/review.test.ts](actions/review.test.ts)), or a route's read the same way ([submit-summary/route.test.ts](../app/api/templates/[templateId]/submit-summary/route.test.ts)). Either checks only what the BFF adds: the parse, the answer's shape, what refreshes, the wording and the layout.
- A read model's wording and layout is a pure function of the service's facts, tested by handing it facts ([queries/versions.test.ts](queries/versions.test.ts)).
- **The contract suite.** What a service decides and writes is one set of cases per area ([services/contract/](services/contract/)), run against the fake and the local implementation (and later the Java API) by the `*.test.ts` beside them. A case sets the backend's clock, acts through the services from the seed, and compares the reads before and after; refusals are compared by code.
- **The database tests below**, for what only the local implementation has (migrations, the seed, the sweeps' SQL, a state the seed lacks and no command makes), and the backend's own surface (`/api/v1`, rendering). The settings and audit reads have a contract run on the local implementation only ([services/contract/settings.ts](services/contract/settings.ts), [audit.ts](services/contract/audit.ts)): the fake has no twin of them until a command's case must observe a change through one.

**A database per test.** A test that touches the database gets a database of its own. The file's database is migrated and seeded once, and every test (and every `beforeEach`) starts from a fresh copy of it, so no test sees another's writes and none needs to clean up. A test that needs more than the seed builds it itself, with a small helper (`submitted()`, `sentBack()`, `approved()`: each calls the one before it), never by relying on what an earlier test left. Don't write a file as a story where each test builds on the last.

Two ways to get one:

- **Code that imports `db`** (the local implementation, or BFF actions run on it end to end): mock the client module with `tempDatabase()`, and call `seededDatabasePerTest()` once at the top of the file. Run the local implementation with a clock of the test's own (`localServices({ clock })`), or mock the clock, the viewer and `next/cache` (`refresh()` works only inside a real server action) to run actions on it. From [actions/versioned-name.test.ts](actions/versioned-name.test.ts):

  ```ts
  vi.mock("@/server/db/client", async () => {
    const { tempDatabase } = await import("@/server/testing/review-fixtures");
    return tempDatabase("ucomp-versioned-name-");
  });
  vi.mock("@/server/services/local/clock", () => ({
    now: vi.fn(async () => env.now),
  }));
  vi.mock("@/server/viewer", () => ({ getViewer: vi.fn() }));
  vi.mock("next/cache", () => ({ refresh: vi.fn(), revalidatePath: vi.fn() }));

  const ids = seededDatabasePerTest({ base: BASE }); // the seed's template ids by key
  beforeAll(async () => {
    ({ db } = await import("@/server/db/client")); // follows each test's copy: keep it in a variable
    people.maya = await loadPersona(db, "maya"); // the seed is the same in every copy
  });
  ```

  `loadPersona(db, id)` builds a `Viewer` the way `getViewer()` does, and `createTemplateWithDraft()` adds a fresh template. A file that needs rows beyond the seed in every test calls `freshDatabasePerTest(build)` with a `build(db)` that adds them, as [services/local/sweeps.test.ts](services/local/sweeps.test.ts) does; `build` gets the build database itself, which only it should use. [db/review-rounds-migration.test.ts](db/review-rounds-migration.test.ts) builds a database as it stood before a migration (`{ migrate: false }`).

- **Code that takes `db` as an argument** (`writeEffects`, `runRender`): `const { db, ids } = standaloneDatabasePerTest({ base })` at the top of the file, as [services/local/effects.test.ts](services/local/effects.test.ts) does. The `db` it returns follows the test's copy.

[src/lib/fresh-database.ts](../lib/fresh-database.ts) is the mechanism, for a database that isn't UCOMP's (the simulator's [actions.test.ts](../simulator/actions.test.ts) uses it on the `sim` schema without importing anything from `src/server`): the exported `db` and `libsql` are stand-ins that follow whichever copy the current test runs on, and each copy is a clone of the seeded file ([decision 0048](../../docs/decisions/0048-every-database-test-gets-its-own-database.md)). `tempDatabase()` opens files the way the app does (`createAppClient`).

**The environment.** `DEMO_MODE` is read once, when [config.ts](config.ts) loads, and Vitest loads no `.env` file, so a test that calls a demo tool says which way it runs: `vi.mock("@/server/config", () => ({ DEMO_MODE: true }))` as the demo contract's runner [services/contract/demo.test.ts](services/contract/demo.test.ts) does, or a getter over a hoisted variable to change it between tests, as [actions/demo.test.ts](actions/demo.test.ts) does.

**Golden files.** [render/golden/](render/golden/README.md) freezes every channel's output for a set of documents, and checks that web, email, and PDF all show the `RenderDoc`'s content. A change that moves one byte of output fails `npm test` until someone regenerates the files with `npm run golden:update` and reads the diff. That README covers adding a case and reviewing a diff. [render/testing/](render/testing/) holds the shared fixture shape, small TipTap JSON builders, and `fresh-process.ts`, which renders in a new Node process for the determinism test.

**Document JSON Schema.** [render/document-json-schema.test.ts](render/document-json-schema.test.ts) checks the committed [docs/reference/document.schema.json](../../docs/reference/document.schema.json) against the generator. It then runs the schema and the document check over every golden case, starter and seeded body, hand-written documents and seeded random mutations, and requires them to agree except for the three rules the schema leaves to code ([render spec](../../docs/render-spec.md) §2). After an editor change that adds a node, a mark or an attribute, run `npm run document-schema:update` and read the diff.

Fixtures: [render/channels/\_\_fixtures\_\_/](render/channels/__fixtures__/) holds hand-built `RenderDoc`s. The import tests read `e2e/fixtures/import/`, generated by its `make-fixtures.mjs`.
