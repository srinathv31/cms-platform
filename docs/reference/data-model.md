# Porting the data model

The schema the Java API builds on MSSQL (Azure SQL), table by table, for the team writing the JPA entities and the
Flyway migrations. It describes the target the owner decided in records 0053 to 0071, and says, table by table, how
today's SQLite schema ([src/server/db/schema/ucomp.ts](../../src/server/db/schema/ucomp.ts)) differs from it.

Most differences change on the Java side only: the Node app keeps its SQLite schema behind lane F's service
interfaces ([0070](../decisions/0070-rules-and-permission-checks-sit-behind-the-service-interfaces.md)). Where the
Node app changes first, the line names who changes it: lane F (the service seam, to-do item 3).

## Conventions

| Column holds                      | MSSQL                                                                                                    | SQLite today                                   | Record                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------- |
| An instant                        | `DATETIME2(3)`, UTC                                                                                      | `INTEGER`, epoch milliseconds read as a `Date` | [0063](../decisions/0063-instants-are-utc-datetime2-ordered-by-at-and-seq.md)   |
| An id                             | `VARCHAR(64)`, generated by the application                                                              | `TEXT`                                         | [0060](../decisions/0060-template-ids-are-random-and-retried-on-a-collision.md) |
| One of a fixed set of codes       | `VARCHAR(n)` with `CHECK (col IN (…))`                                                                   | `TEXT`, typed in TypeScript only               | [0062](../decisions/0062-invariants-hold-in-the-database-not-in-one-writer.md)  |
| A flag                            | `BIT`                                                                                                    | `INTEGER` 0 or 1                               |                                                                                 |
| A count or a number               | `INT`; a `seq` is `BIGINT`                                                                               | `INTEGER`                                      |                                                                                 |
| Text a person writes              | `NVARCHAR(n)` or `NVARCHAR(MAX)`                                                                         | `TEXT`                                         |                                                                                 |
| A document or record kept as JSON | `NVARCHAR(MAX)` with `CHECK (ISJSON(col) = 1)`, or Azure SQL's native `json` type, by the DBA's standard | `TEXT` holding JSON, typed in TypeScript only  | [0061](../decisions/0061-documents-stay-json-and-references-become-rows.md)     |

- **Instants.** The Java `Clock` ticks in milliseconds (`Clock.tick(base, Duration.ofMillis(1))`), so a value read
  back equals the one the domain compared, and the Hibernate mapping for `Instant` is set explicitly (Hibernate 6
  maps it to `datetimeoffset` otherwise). Instants cross every boundary as ISO strings: read models, `/api/v1`, and
  JSON that stays JSON. A day is a `YYYY-MM-DD` string; no column stores one. Day buckets are `CAST(at AS DATE)`, UTC
  days ([0028](../decisions/0028-today-and-yesterday-are-utc-calendar-days.md)); a sunset's day is in the business
  time zone ([0017](../decisions/0017-a-sunset-date-ends-at-midnight-in-the-business-time-zone.md)).
- **Lengths.** Where a column's notes name a constant, the length is the limit the code enforces today. JavaScript's
  `length` and `NVARCHAR(n)` both count UTF-16 code units, so they agree. Every other length is a proposal: the code
  sets no limit there. The Java side enforces the limit it picks as a refusal, never by truncating.
- **Ids.** Every id is an opaque string the application generates. Most are a prefix and ten random Crockford base32
  characters (`newId` in [src/server/ids.ts](../../src/server/ids.ts): `v_…`, `ae_…`). A template's is `UC-` and six
  ([0060](../decisions/0060-template-ids-are-random-and-retried-on-a-collision.md)), a user's is Better Auth's
  ([0054](../decisions/0054-users-are-better-auth-users-linked-to-entra-by-oid.md)), and a team's is opaque and never
  its slug ([0053](../decisions/0053-team-ids-are-opaque-and-slugs-resolve-at-the-url.md)). Only the template id is
  checked for a collision: on a key violation, the whole transaction is retried with a new id, at most three times.
- **Log tables cluster on `seq`.** `render_log`, `audit_events` and `notifications` get `seq BIGINT IDENTITY` as
  their clustered key; `id` stays unique and nonclustered, and can stay the JPA `@Id`. Rows that share an instant
  are ordered by `seq` (`ORDER BY at DESC, seq DESC`) where SQLite uses `rowid` today: the Audit page
  ([src/server/queries/audit.ts](../../src/server/queries/audit.ts)), the Activity tab (`activity.ts`) and the bell
  (`notifications.ts`). `consumer_notices` clusters on its own `seq`, which the notice counter assigns in commit
  order: an IDENTITY isn't commit-ordered ([0062](../decisions/0062-invariants-hold-in-the-database-not-in-one-writer.md)).
- **References.** "FK" is a declared foreign key, as today. "No FK" is a column that names a row in another table on
  purpose without one: a log or a record that outlives what it names. Which of these gain a foreign key is part of
  the deletion question ([Open questions](#open-questions-for-the-handoff)).
- **Flyway, not annotations,** holds the filtered unique indexes (unique over the rows a `WHERE` selects) and the
  CHECKs: Hibernate generates neither. MSSQL's unique indexes treat NULLs as equal, where SQLite's keep them distinct.
- **A CHECK can't hold a subquery** on MSSQL, so a CHECK on the values inside a JSON array calls a scalar function
  over `OPENJSON`. Where the choice is "JSON with a CHECK, or a child table", the child table is the simpler.
- **Collation.** MSSQL's default collation is case-insensitive; SQLite compares bytes. Ids, slugs and keys are
  written in one case, so their unique indexes behave the same. Search orders names under a binary collation,
  `Latin1_General_100_BIN2` ([0059](../decisions/0059-template-search-ranks-and-pages-in-sql.md)).
- **`versions.rev` is JPA's `@Version`.** The compare-and-set predicates the actions write, on `rev` and on `state`,
  stay: under read committed snapshot an `UPDATE` reads the latest committed row and locks it.

## Invariants that hold today only because SQLite has one writer

Every write in the Node process takes turns on one lock (`src/lib/serialized-writes.ts`) inside `BEGIN IMMEDIATE`, so
a read-check-write can't interleave with another. Azure SQL runs read committed snapshot by default, where a plain
`SELECT` reads the last committed row without locking, and two API instances run at once. Each rule below gets a
database mechanism instead ([0062](../decisions/0062-invariants-hold-in-the-database-not-in-one-writer.md)). Two rows
rest on SQLite's semantics rather than its one writer, and port the same way: NULLs in a unique index, and `rowid`.

| Invariant                                                          | Today                                                                                           | On MSSQL                                                                                                                                                                                                                       |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Notices are numbered in commit order, and a number is never reused | `takeNoticeSeqs` reads `settings.consumer_notice_seq` and `MAX(seq)`, then writes               | `UPDATE notice_counter SET last = last + @n OUTPUT inserted.last` inside the writing transaction: the row lock is held to commit, so the next writer waits and numbers after it. Not a `SEQUENCE`, which isn't commit-ordered. |
| One pending access request per person and team                     | `requestAccess` (`src/domain/access/requests.ts`) reads, then inserts                           | Filtered unique index on `access_requests`                                                                                                                                                                                     |
| One open recertification per team                                  | `startRecert` (`src/domain/access/recertification.ts`) reads, then inserts                      | Filtered unique index on `recertifications`                                                                                                                                                                                    |
| A team keeps an active Team Admin                                  | `losesLastAdmin` (`src/domain/access/members.ts`) reads the memberships, then the action writes | Every membership change, the sweep's included, locks the team row first (`UPDLOCK, HOLDLOCK`, or `PESSIMISTIC_WRITE`), so two admins can't demote each other                                                                   |
| One row per round of a number                                      | Unique `(template_id, number, round)`; drafts pass because SQLite keeps NULLs distinct          | The same index with `WHERE number IS NOT NULL`                                                                                                                                                                                 |
| Template ids are unique                                            | `withNewTemplateId` inserts, and draws again when the id is taken (local and fake)              | Insert, and retry the whole transaction with a new id on a key violation, at most three times ([0060](../decisions/0060-template-ids-are-random-and-retried-on-a-collision.md))                                                |
| A save or a transition applies to the row it read                  | `UPDATE … WHERE rev = @rev AND state = …`, safe under `BEGIN IMMEDIATE`                         | The same predicates, and `rev` as `@Version`: an `UPDATE` reads the latest committed row and locks it                                                                                                                          |
| A passed sunset is recorded once                                   | The sweep skips a version with a `version.sunset_passed` audit row                              | `versions.sunset_recorded_at`, set in the sweep's transaction with `WHERE sunset_recorded_at IS NULL`, so two sweeps can't both record it                                                                                      |
| Rows written by one action keep their order                        | `rowid`                                                                                         | `seq`, ordered `(at, seq)` ([0063](../decisions/0063-instants-are-utc-datetime2-ordered-by-at-and-seq.md))                                                                                                                     |
| A column holds one of its codes                                    | TypeScript types only                                                                           | A CHECK on every enum column (each table above)                                                                                                                                                                                |

The other version rules already hold in the database today and port as they are: one open draft, one Active version,
and one released row per number, as filtered unique indexes.

## Logs

The audit log and the render log are kept differently
([0066](../decisions/0066-the-audit-log-is-the-record-and-render-events-roll-up.md)).

- **`audit_events` is the system of record.** Relational, append-only, and forwarded to the log platform or SIEM.
  Retention, immutability (write once) and forwarding follow the enterprise's records standards. The Audit page, its
  CSV export and the Activity tab read it. `draft.edited` stops being updated in place: one row per save, or an
  edit-session table with one audit row when the session ends, the Java team's choice.
- **No business rule reads the audit log.** Two do today, and both move to the version row:
  - The sunset sweep's "once" (`recordedSunsets` in `src/server/services/local/sweeps.ts`) checks for a
    `version.sunset_passed` row; it becomes `versions.sunset_recorded_at`. The audit row is still written, dated at
    the sunset ([0026](../decisions/0026-a-passed-sunset-is-recorded-by-a-sweep.md)).
  - Autosave's recovery from a lost response (`sessionOwnsRev` in `src/domain/lifecycle/autosave.ts`, given what `lastSaveOf` in
    `src/server/services/local/drafts.ts` reads) reads the
    session's `draft.edited` row for the `rev` it produced; it becomes `versions.last_save_session` and
    `last_save_by` beside `rev` ([B5](../handoff-review.md#b5--medium-autosave-conflict-recovery-reads-the-audit-log)).

  Lane F (to-do item 3) puts both reads behind named service methods, so the Java implementation answers them from
  columns.

- **`render_log` keeps raw events for a window**, about 13 months, deleted by a retention job, and sends them to the
  log platform for operations. Usage's list of recent failures reads the raw rows.
- **`render_daily` serves everything else**: Usage's windows, trend and heatmap; each version's last render; the
  integration panel's latest consumer; and the 90-day audience of a consumer notice
  ([0032](../decisions/0032-consumers-are-told-when-a-sunset-passes.md)). How it's kept current (an upsert per
  render, or a job) is the Java team's choice.

## Payloads

Each audit action and notice kind gets one shape, which the runtime and the seed both write, holding facts only: ids,
numbers, instants, codes, and names as they were at the time, never a sentence
([0064](../decisions/0064-payloads-are-facts-with-one-shape-per-event.md)). The tables below are the runtime's
shapes, read from the effect builders on 2026-10-12; where the runtime itself still differs from them, a list after
each table says so. This is the catalogue the Java side's event DTOs (or the JSON columns' validation) are
generated from; the builder named in each row is the source of truth.

Types: `int`, `boolean`, `string`; `instant` is an ISO string; `day` is `YYYY-MM-DD`; `zone` is an IANA name; a role
is a team role code; `outputs` is a list of output keys (`pdf`, `web`, `email`, `push.ios`, `push.android`, `sms`,
from `src/domain/review-outputs.ts`). A field marked "as it was" is a name copied at the time, never looked up again.
"Absent unless …" is a field written only in that case.

### Notification kinds

A notification stores its kind, the kind's `facts` and a `link`; `body` holds a person's own words and nothing else
([0055](../decisions/0055-notifications-store-facts-and-are-worded-on-read.md)). `describeNotification`
(`src/domain/notifications.ts`) words the facts when the bell reads them, for the person reading: one about a member
(`userId`) reads "Your access…" to that member and "Devon Lin's access…" to anyone else. The declared types are
`NotificationFacts` (`src/domain/review-types.ts`) and `AccessNotificationFacts` (`src/domain/access-types.ts`). A
version is named by `templateName` (as it was), `number` and, for a round, `round`; whether the words show the round
is `versionLabel`'s rule (`src/domain/rounds.ts`), applied when read. Names (`actorName`, `userName`, `teamName`,
stage names) are as they were. A recertification's quarter label (`Q1 2027`) is worded from its deadline, never
stored. The writers are `writeEffects` and `writeAccessEffects` (`src/server/services/local/`), from the builders in
`src/domain/lifecycle/`, `comments.ts`, `access/` and `platform-config/`.

## What isn't ported

- **The simulator's tables.** `sim_offers`, `sim_customers`, `sim_links`, `sim_deliveries` and `sim_notice_reads`
  ([src/server/db/schema/sim.ts](../../src/server/db/schema/sim.ts)) are Coral's own system, a demo consumer that
  reaches Stencil only over `/api/v1`. They stay with the demo.
- **Demo state.** `settings.clock_offset_days` and `seed_version`, and `users.is_persona`, exist only where
  `DEMO_MODE` runs ([0051](../decisions/0051-the-demo-tools-run-only-in-demo-mode.md)). The Java API's equivalent of
  the clock offset is a test-only setting ([0068](../decisions/0068-the-bff-is-tested-against-a-fake-and-one-contract-suite.md)).
- **The seed.** Java loads a JSON fixture the Node seed exports, with literal template and version ids and times as
  days before the load ([0069](../decisions/0069-seed-ids-are-literal-and-the-seed-exports-a-fixture.md)). Test
  data stays out of the production migrations.
- **The migration history.** The fourteen files in `src/server/db/migrations` built the prototype's SQLite file step
  by step. Flyway starts from the target on this page; there is no data to carry over.
- **SQLite scaffolding.** The write lock (`src/lib/serialized-writes.ts`), the per-test database clone
  (`src/lib/fresh-database.ts`) and the Turso path in `drizzle.config.ts` have no MSSQL counterpart.

## Open questions for the handoff

- **Deletion and cascades.** What can be deleted (a template, a team, a user) and what outlives what. Nothing is
  deleted today. The "no FK" references above are `versions.based_on_version_id` and `import_upload_id`,
  `approvals.stage_id`, `version_stages.stage_id`, every reference in `render_log` and `render_daily`, `audit_events`
  except `actor_id`, `consumer_notices` except `consumer_id`, and `notifications.team_id`.
- **Better Auth's tables in the same database.** How its `user`, `account`, `session` and `verification` tables map
  onto `users`, and whether its Microsoft account id is `sub` (per app) or `oid` (per tenant)
  ([0054](../decisions/0054-users-are-better-auth-users-linked-to-entra-by-oid.md)).
- **People named before they sign in.** An approval stage can name a person who has no `users` row yet: a Graph
  lookup or provisioning creates it.
- **Lengths with no limit in the code.** The columns above that name no constant (user names, titles and emails,
  content type and consumer names, the SMS footer, a team's app name and sender, a recertification's label): agree on
  each, and enforce it in the domain.
- **CHECKs on `audit_events.action` and `notifications.kind`.** Record 0062 lists the other enum columns, not these;
  a CHECK there makes every new event kind a migration.
- **Chain edits against a concurrent submit.** A chain edit refuses to remove a stage that versions wait on, by
  reading them first ([B3](../handoff-review.md#b3--medium-invariants-rely-on-sqlites-single-writer)); nothing yet
  stops a submit recording that stage at the same moment.
- **The JSON storage type**, native `json` or `NVARCHAR(MAX)` with `ISJSON`: the DBA's standard
  ([0061](../decisions/0061-documents-stay-json-and-references-become-rows.md)).
- **Retention.** How long `render_log`'s raw window and `audit_events` are kept, set by the enterprise's records and
  observability standards ([0066](../decisions/0066-the-audit-log-is-the-record-and-render-events-roll-up.md)).
- **A readable template id and the `UC-` prefix**: product owner questions
  ([0060](../decisions/0060-template-ids-are-random-and-retried-on-a-collision.md)).
- **A consumer registry.** Nothing creates a `consumers` row or links it to an app registration; consumers come from
  the seed ([0057](../decisions/0057-consumers-authenticate-with-client-credentials.md)).
